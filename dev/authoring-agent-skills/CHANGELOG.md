# Changelog

## 1.4.0 (2026-11-27)

Fixes from an audit of 1.3.0. The task evals and trigger evals have not been re-run; they need a headless agent CLI.

Lint (`lint_skill.py`):
- Change calls. The lint now knows two groups. Local changes: `os.remove`, `os.replace`, `shutil.rmtree`, `shutil.move`, `rm` in a shell line or an argument list, `git merge`, `git clean`, `git reset --hard`, `git worktree remove`, `git branch -D` and `git checkout ... --` (a file restore; a plain `git checkout <branch>` is not reported, in any form). A git subcommand that only starts with one of these words, such as `git merge-base`, is not reported. Changes outside the machine or repository: `git push`, `requests.post` and the like, `method="POST|PUT|PATCH|DELETE"`, `smtplib`, `curl -X`, `kubectl` and `terraform` apply or delete, `DROP TABLE`, `DELETE FROM`, `TRUNCATE`, `npm publish`, `cargo publish`, `twine upload`, `gh pr merge`, `docker push`, `aws s3 rm`. It does not know every form; see "Known gaps" below.
- Git commands. A git command is found as text (`git push` in a shell line or a command string) and as arguments. As arguments it is read from a list or tuple that holds the string `"git"`, or from a call to a git helper: a function named `git`, alone or with words from a fixed list around it (`run_git`, `_git_out`, `gitCmd`; not `git_log`, `git_branch_exists` or `github_events`). The subcommand is the first string after `"git"` (in a helper call: the first string) that is not an option, and the argument after `-C`, `-c`, `--git-dir`, `--work-tree` or `--namespace` is skipped as that option's value. So `git(str(top), "push")`, `git(top,"merge")` and a call spread over several lines are reported, and `git(top, "rev-parse", "push")`, `git_log(top, "--grep", "push")`, `git(top, "log"); other("push")` and `OPS = ["worktree", "remove", "branch", "-D"]` are not. A first version of this release paired `"git"` or a name starting with `git` with any later `"push"` on the line, and reported `"worktree", "remove"`, `"branch", "-D"` and `"checkout", ..., "--"` in any list.
- Python files are read with the standard `tokenize` module. Comments and docstrings are left out of every check, and a string literal is told apart from code. A docstring is a statement that is nothing but string literals (not an f-string), wherever it stands. Any other string is a value and its text is checked like code (`USAGE = """..."""`, a command string). A `.py` file that does not tokenize, or that has a line of over 5,000 characters (the tokenizer of Python 3.12 takes minutes on a line of 1 MB), is read line by line like a shell file, and the lint says so in a warning ("not read as Python"): then its docstrings, and its comments after code, count as code. Before, patterns looked for triple quotes; a `"""` inside a one-line string or a comment made them drop the code up to the next docstring, and an f-string on its own line was dropped as a docstring.
- `--dry-run` counts only where the script defines or tests the flag. In a `.py` file that is a string literal that holds the flag and nothing but flags (`"--dry-run"`, `"-n, --dry-run"`, `"--dry-run/--no-dry-run"`) in one of these places: a positional argument of `add_argument(...)`, `add_option(...)`, `option(...)` or `Option(...)`; next to `==` or `!=`, or before `in` or `not in`; an item of a list, tuple or set that follows a membership `in` (`arg in ("-n", "--dry-run")`, on one line or several; not the list of a `for` loop); the argument of `.count(...)`, `.index(...)`, `.remove(...)` or `.startswith(...)`; a pattern of a `case` line. A parameter `dry_run:` also counts in a file that names `typer`. In a `.sh`, `.js` or `.ts` file it is: the first string of an option call, after up to three short flags, with or without the two dashes (commander, yargs `.option('dry-run', ...)`); a shell `case` label, alone or with alternatives and spaces (`--dry-run | -n)`, `-n | --dry-run )`, `--dry-run=*)`); a comparison with `==`, `===` or `!=`; a shell test with a single `=` (`[ "$1" = --dry-run ]`); `includes`, `indexOf` or `has` with the flag alone; a JavaScript `case "--dry-run":`; a `"dry-run": {` key in an options object (Node `parseArgs`). In a `.py` file a mention in a comment, a docstring, a help text, an f-string, an assignment (`OPT = "--dry-run"`, `MSG = "--dry-run is ..."`) or the arguments of another tool does not count. In a shell or JavaScript file most mentions do not count either, but the check there reads lines, not the language; "Known gaps" lists what it still takes for the flag.
- Waiver. `lint: no-dry-run: <reason>` must be a comment, on its own line or after code, with a reason of three words or more. A string literal does not waive. The waiver is still per file and covers local changes only; a change outside the machine is reported with or without it.
- Scripts scan. Skipped: `node_modules`, `venv`, `vendor`, `third_party`, `__pycache__`, `fixtures`, `dist`, `build` and any folder whose name starts with a dot. Test files (`test_*`, `selftest`, anything under `tests/`) get no `--dry-run` warning. A symlink or a special file is named in a warning and not read.
- Interactive check. `input(` is checked in `.py` files only and not inside a docstring or a comment. New: `getpass.getpass(` and shell `read` with a `-p` flag after up to ten other flags, each with or without a value (`read -rp`, `read -r -p`, `read -t 5 -p`).
- Paths. A `#fragment`, a link title and a trailing `?`, `!`, `*`, `]`, `}`, `|` or `>` are no longer part of a path. A path in bold, behind a `${...SKILL...}/` variable or written with a backslash is now checked. Paths named inside `references/*.md` are checked too. A bare path whose folder the skill does not have is a warning (it may be a path in the user's project); a Markdown link, or a path in a folder the skill has, stays an error. A leading `./` is the skill root too, so `./scripts/x.py` is checked like `scripts/x.py`. A Markdown link in a reference may climb to another file of the skill (`../scripts/x.py`, `../SKILL.md`): it is checked against the disk, and a missing file is an error. A link that leaves the skill is still a warning. A path behind a placeholder such as `<dir>/scripts/x.py` is not checked.
- One level deep. The warning now fires when a reference names an `.md` file that SKILL.md does not name, in either link form. A reference that names a file SKILL.md also names is allowed.
- Description. Third-person verbs ("Deploys", "Publishes") now match the side-effect check, and words after "Not for" do not. The hint no longer names one host's frontmatter key. "I/O" is no longer read as first person. An XML or HTML tag is a warning.
- Frontmatter. A UTF-8 byte order mark is accepted. A YAML comment after an unquoted value is dropped. Escapes in a double-quoted value are decoded before the length is counted. `compatibility` over 500 characters is an error.
- Body. A 499-line body with a final newline was counted as 500; it is now 499. A `TODO` left in SKILL.md is a warning.
- Eval files. `evals.json` must be an object with an `evals` array. Each trigger entry needs a string `query` and a true or false `should_trigger`.
- Exit codes. 2 now also means the lint could not run: the skill folder or `--evals-dir` is not a folder (a file, or a name too long for the file system; the second ended in a traceback with exit 1 on Python 3.12), or a file is unreadable or not UTF-8. The message goes to stderr and nothing to stdout. Deeply nested JSON is a lint error. No file is read past 1,000,000 characters. A path whose name is too long for the file system is a "does not exist" error (or the "not in this skill" warning) on every Python version, not exit 2.
- Speed. The inputs found slow so far are fast now: a script of 60,000 blank lines took 19 s and a reference holding 60 KB of `](` 114 s; a script holding `git_` 50,000 times took 23 s, a shell script with 3,000 `read` commands each followed by 95 spaces 14 s, and a reference naming one file 99,000 times beside a 900 KB SKILL.md 4 s. Each now takes about a second or less. For this, every gap inside a pattern has a fixed maximum: 400 characters on one line between `curl` and `-X`, 200 between `git checkout` and `--`, 80 characters of white space between two arguments, six arguments between a git helper's bracket and the subcommand in a shell or JavaScript file, ten flags before `-p`, 500 characters each for a link target and its fragment, and 40 on each side of `SKILL` in a `${...SKILL...}` variable name. A form past one of these limits is not found. A path named again in the same file is looked up on disk once. This is not a proof that no input is slow: the selftest lints the inputs written to be slow under one time limit, and a new pattern needs a new input there. The slowest input known is a 1 MB `.py` file of short dense lines, which takes about 3 s on Python 3.12 and 1 to 2 s on 3.13, nearly all of it in the tokenizer.
- Known gaps. These are not found, or found wrongly, and are left so:
  - A git command built from parts is not reported: arguments from a variable or `*args` (`git(*cmd)`), a string put together (`"pu" + "sh"`, `mode or "push"`), an f-string, `repo.git.push()`, a helper with a name outside the fixed list (`vcs("push")`).
  - A git command with an option between `git` and the subcommand in a shell line or a command string is not reported (`git -C dir push`, `git --no-pager merge x`); in an argument list or a helper call it is.
  - `git checkout $(cmd) -- file` in a shell line is not reported, because the search for `--` stops at `)`.
  - In a shell or JavaScript file a git helper call is followed only while the arguments before the subcommand are bare names or options, at most six of them; `runGit(dir(), "push")` is not reported.
  - A `--dry-run` flag read in another way is not seen, so the script gets the warning although it has the flag: `getopt`, `docopt`, `minimist`, a flag held in a variable (`FLAG = "--dry-run"; if FLAG in args`), a `case ("-n" | "--dry-run"):` pattern in brackets, a flag defined in another file. Add the waiver comment for a local change, or test the flag in one of the listed forms.
  - In a shell or JavaScript file, text in a string or in a comment after code is read as code. So `echo "run git push by hand"` is reported, and these are taken for the flag: a line that starts with `--dry-run)` inside a multi-line array or command, `x == "--dry-run"` inside a string, a comment after code that holds a listed form.
  - In a `.py` file a string that is an argument or a value is checked as text, so `print("then run git push")` and `HELP = "rm -rf is never used"` are reported. Only comments and docstrings are left out.
  - A `.py` file with a line of over 5,000 characters, or one that does not tokenize, is read line by line, with the warning named above.
  - The waiver is per file, not per call: one waiver comment covers every local change in the file.

Other scripts:
- `scaffold.py`: a description with a control character (a newline, for example) is refused with exit 2. The description is escaped once, in a form valid in both JSON and a double-quoted YAML value, so backslashes and quotes survive. Nothing is written through a symlink inside the new folder: if `<dest>/<name>`, or a folder or file to be written in it, is a symlink, the run is refused, also with `--force`. `--dest` itself may be a symlink or lie under one, as a linked skills folder does. A target that cannot be written is exit 2 with a one-line message. The run now looks at every file and folder it is to write before it writes the first one: a file where a folder has to be (or the reverse), a file that may not be overwritten, a folder that may not be written in, a name too long for the file system. On any of these it writes nothing and exits 2; before, `--force` with a file named `evals` in the target overwrote SKILL.md and three other files and then stopped, and a `--dest` name of 300 characters or a `--dest` under a folder without access ended in a traceback with exit 1. `--dry-run` makes the same checks and exits with the same code and message as the run without it; before, `--dest <a file> --dry-run` was exit 0 and the real run exit 2. A target that changes between the check and the write can still stop a run part way (exit 2). A description that holds U+0085, U+2028 or U+2029 (line breaks to some YAML readers), or bytes that are not UTF-8, is refused with exit 2 before any file is written; before, the first two wrote a description that such a reader could split into a second key, and the last ended in a traceback with an empty SKILL.md left behind.
- `score_trigger_evals.py`: `should_trigger` and `triggered` must be JSON true or false and `query` a string. A line of the wrong shape, a line nested too deeply to parse, a file that is not UTF-8, a file with no runs and two runs of one query with different `should_trigger` are exit 2. A query that holds U+0085, U+2028 or U+2029 no longer splits its line in two, and a query with a lone surrogate (`"\ud800"`) is scored; both ended in exit 2 or a traceback before.
- `assets/redirect-skill.md`: the host-specific `user-invocable` key is replaced by a comment, so the template passes `--portable`.

Guidance:
- `references/authoring.md`: the waiver text matches the lint. Dependencies are "the standard library alone, or inline script metadata with pinned package versions", and a split script keeps the entry script's rule. Removed the clause about content in the middle of a long context, which had no listed source.
- `references/decide.md`: a script that changes things needs `--dry-run`; the `--confirm` requirement is gone. "One level deep" is defined as: SKILL.md names each reference.
- `references/evals.md`: at least 3 cases to start, growing towards 10 to 50. Both arms of a task eval start together, each in its own clean run.
- `references/ship.md` and step 9: a plain skill holds the version in `metadata.version`; a plugin holds the same string in every manifest too.
- `references/sources.md`: the sentence on Vercel's evals says only that wording changed the results. It was not re-read for this release.
- `references/authoring.md`, frontmatter and paths: says how the lint reads a path (a bare path from the skill root, with or without `./`; a Markdown link from the file that holds it, so a reference links to a script with `../`).
- `references/runtime.md`: the example path `references/playbook.md` is now `references/<topic>.md`, because the lint checks paths in references.
- SKILL.md: step 7 explains exit code 2. New gotcha: check the scaffolded plugin manifests against each host's manifest reference.

Evals and tests:

- New eval 6 with the fixture `evals/files/fixture-skills/notes-keeper/`, a skill that sits at its own 20-line cap. It checks the size-limit rule from 1.3.0. Learning L-0002 records that rule. Its first expectation is that SKILL.md still has its 20 lines, the three blank lines still blank and in place, and every other line unchanged or with text added at its end. The first wording named only the "Never" lines and the checklist steps, so a run that deleted a blank line to make room for a new line passed. The two honest outcomes are a load condition added to the end of an existing line, or no change and a report; the selftest checks that both pass the expectation and that the blank-line cut fails it.
- `selftest.py` holds a table with one small script per documented form: every call in the two change groups, every way to define or test `--dry-run` and every mention that must not count, the waiver in each accepted and each refused form, docstrings in each spelling, the interactive prompts, each skipped folder and each kind of test file. Further tables cover the frontmatter and description rules at their edges, the path rules, the exit codes of the three scripts and the inputs that used to be slow. A first version of this entry said the selftest had an assertion for each change above; a second review removed 48 behaviours one at a time and that selftest still passed for 41 of them. Against this selftest, the same 48 single-line mutants and 49 more for the behaviours added since (97 in all) each make it fail. Five of the 97 make a pattern slow again and fail it through the 120-second limit on one lint run. Two fail it only on a Python that still raises for an over-long file name or deeply nested JSON (3.12 does); on a newer one those two cases pass with or without the fix. The assertion on `scripts/notes.py` now puts a real call in a comment; before, it could not fail. A third review of that selftest found six more mutants it passed for (a `-D` read as `-d` too, a gap limit moved from 400 to 40, three of the line separators in `score_trigger_evals.py`, a file given as the skill folder), a row that passed for the wrong reason, and that the slow inputs could only fail through a 120-second limit. Rows for each are added, and the patterns those mutants were in are replaced or have a row at their limit. The inputs written to be slow are now linted in one run with a limit of 40 seconds; that run takes about 3 seconds, and each of the two new pattern inputs takes over a minute alone with the old pattern (71 s and 66 s). The selftest takes 7 to 9 seconds on Python 3.12 and 6 to 7 on 3.13, up from 5 to 6 on the same machine.
